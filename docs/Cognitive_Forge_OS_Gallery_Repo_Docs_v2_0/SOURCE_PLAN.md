# Cognitive Forge OS 고도화 개선 작업 지시 레포 문서 세트 도출 계획

- 문서 버전: v1.0
- 작성일: 2026-11-01, 한국 시간
- 전달 대상: cognitive-forge-os 제품·설계·개발·QA 담당 팀
- 대상 프로젝트: C:/Users/User/cognitive-forge-os
- 문서 성격: 고도화 작업을 지시할 레포 문서 세트의 제작 계획
- 이번 산출 범위: 목표 제품, 문서 구성, 작성 순서, 계약·예시 산출물, 검수 기준, 구현 배치 연결
- 상태: 제안 계획. 본문에 열거한 명세·스키마·테스트·연동 기능은 향후 도출 또는 구현 대상이며, 이미 완성된 것으로 표시하지 않는다.

## 1. 팀이 먼저 공유할 제품 목표

Cognitive Forge만으로 전문가나 실무자가 자신의 지식과 업무 사례를 작은 AI 서비스로 만들고, 실제 자료로 시험하고, 이용 화면을 배포하고, 실행 결과를 검수·보관할 수 있게 한다. 다른 보유 프로젝트와의 연결은 선택 사항으로 둔다. 모델 API와 데이터베이스 등 기본 운영 인프라는 필요하지만, TF-Studio·DualBrain OS·KHERE·AI홈피가 설치되어 있어야 기능하는 구조를 만들지 않는다.

대표 사용 경험은 다음과 같다. 제작자가 “기업 자료를 받아 회사 소개와 FAQ를 만들어 주는 서비스”를 선택하고, 자신의 좋은 작업 사례와 검수 기준을 넣는다. Forge가 입력 양식·작업 절차·결과 화면·평가 항목을 제안한다. 제작자는 예시 자료로 실행한 결과를 보며 기준을 수정하고, 승인한 버전을 앱으로 배포한다. 고객이 자료를 제출하면 부족한 정보를 질문하고, 근거를 확인하며 작업한 뒤 결과를 제공한다. 전문가 검수가 필요한 작업은 Forge 안에서 검수하고, 승인본과 수정 이력이 남는다.

이 제품의 두 가지 성공 조건은 동시에 충족되어야 한다.

1. 비개발자가 JSON이나 그래프 문법을 배우지 않고도 유용한 마이크로 에이전트를 만들 수 있다.
2. 외부 서비스가 같은 에이전트를 API로 실행하고, 상태와 산출물을 받아 자신의 업무 흐름에 연결할 수 있다.

두 조건은 하나의 실행 서비스와 계약 위에서 구현한다. 작성 화면, 공개 앱, 외부 API마다 별도의 AI 실행 로직을 만들지 않는다.

## 2. 이번 고도화에서 확정할 경계

### 2.1 Forge 자체가 책임질 기본 기능

독립 운영을 위해 제작자 계정과 작업공간, 템플릿 선택, 사례·지식 등록, 입력·출력 화면 작성, 시험 실행, 평가 결과 확인, 버전 발행, 고객 실행, 질문·검수 대기, 산출물 보관·내보내기, 사용량과 오류 확인을 Forge 안에 둔다.

기본 검수 화면과 산출물 이력은 외부 Work OS 연결 없이 작동해야 한다. 전문가 검수가 포함된 서비스에서도 Forge의 인증된 담당자가 결정하고 실행을 이어갈 수 있어야 한다. 모델 연결·자료 저장·작업 큐 등 필수 인프라의 설치 및 설정 방법은 운영 문서에 포함한다.

### 2.2 선택적으로 연결할 기능

TF-Studio에서는 교육 과정과 제작 과제를 보내거나 시험 결과를 받아갈 수 있다. DualBrain OS는 외부 프로젝트와 산출물 관리를 연계할 수 있다. KHERE는 주문·수행자 매칭·거래 상태를 관리할 수 있다. AI홈피는 에이전트 소개와 이용 진입점을 제공할 수 있다. CRE-Dealcard는 특정 문서 작업의 자료나 결과를 교환할 수 있다.

외부 시스템의 주문, 강의, 프로젝트 상태는 그 시스템이 소유한다. Forge의 CasePack 버전, 실제 실행 상태, 도구 실행 기록과 원본 산출물 버전은 Forge가 소유한다. 승인 권한을 외부에 위임하는 경우에는 작업 생성 시 권한 주체를 명시하며, 실행 중 두 시스템이 서로 다른 승인을 원본으로 기록하지 않도록 한다.

### 2.3 최초 출시 범위를 제한할 항목

최초 범위는 문서 중심 마이크로 에이전트와 전문가 검수까지로 정한다. 자유로운 범용 멀티에이전트 편성, 전 분야 마켓플레이스, 외부 거래·정산 엔진, 무제한 자율 실행은 후속 범위다. 이미지·코드·조사 업무는 같은 계약을 확장할 수 있도록 설계하되, 각 분야의 생성 도구·검사기·권한은 별도로 검증한다.

외부 결제나 매칭이 없어도 제작·실행·검수·납품을 시연할 수 있어야 한다. 유료화에 필요한 이용 권한·사용량 기록의 확장 지점은 마련하되, 복잡한 거래 플랫폼 구축을 기본 제작 기능의 선행 조건으로 두지 않는다.

## 3. 현재 코드와 문서에서 출발하는 방법

현재 CasePack-MAO에는 TASKFLOW-CX, 입력 계약, 출력 계약, 실행 설정, 화면 규격이 묶여 있다. Graph와 Bridge를 통한 연결 실행, 결과 형식 검증과 실행 기록의 구조도 존재한다. 이를 보존하면서 고도화한다.

검토한 공개 실행 구성은 MockAIProvider를 사용하며, provider factory의 실제 제공자 경로는 미구현으로 표시되어 있다. evals와 policy_pack은 구체적인 실행 계약이 확정되지 않은 유연한 JSON이다. 순차 그래프 실행만으로 사람 응답 대기, 서버 재시작 후 재개, 외부 도구 권한까지 구현되어 있다고 해석하면 안 된다.

B0에서는 이러한 관찰을 최신 코드에서 다시 확인하고, 다음 네 상태로 분류한다.

- 구현됨: 실행 경로를 소스로 확인한 상태.
- 부분 구현: 정의나 일부 경로가 있으나 제품 흐름이 완결되지 않은 상태.
- 문서에만 있음: 설계 의도만 확인한 상태.
- 확인 필요: 근거가 부족하거나 실행 검증이 필요한 상태.

테스트 파일이 있다는 이유로 통과로 기록하지 않는다. 실행하지 않은 검사는 NOT_RUN으로 표시한다. 실제 모델 호출, 배포 환경, 저장소별 데이터 보존, 작업공간 격리는 별도 증거가 필요하다.

기존 문서는 docs/core의 01_Platform_Master_PRD.md, 02_Platform_Master_SDD.md, 03_Object_Standards.md와 docs/implementation의 04~08 명세를 확인 대상으로 삼는다. 새 문서 세트에는 각 기존 문서를 유지·개정·대체·참조 중 어느 방식으로 처리할지 기록한다. 서로 다른 두 PRD나 객체 사전이 동시에 정본으로 남지 않게 한다.

## 4. 요구사항 식별자와 완료 조건

문서, 개발 티켓, 예시와 테스트는 아래 식별자를 공유한다. 단순히 특정 기능을 설명한 것과 실제로 완료 기준을 충족한 것을 구분한다.

| ID | 요구사항 | 제품 수준 완료 조건 |
|---|---|---|
| R01 | 독립 운영 | 다른 사업 시스템 연결 없이 가입·작성·시험·발행·실행·검수·내보내기를 완주 |
| R02 | 쉬운 제작 | JSON 편집 없이 템플릿·자연어·실제 사례 중 한 경로로 초안 작성 |
| R03 | TASKFLOW 변환 | 사람이 작성한 내용과 실행 계약·평가 규칙의 대응을 추적 |
| R04 | 지식과 근거 | 참조 지식·고객 자료·예시를 분리하고 결과에 사용한 자료 버전을 식별 |
| R05 | 실제 실행 | 실제 모델의 결과·오류·비용·지연을 기록하고 모의 실행과 구분 |
| R06 | 작업 이어가기 | 추가 질문·검수 대기·실패 후 필요한 지점에서 재개 |
| R07 | 품질 평가 | 생성·형식 검사·업무 평가·사람 검수 상태를 분리 |
| R08 | 검수와 산출물 | 정확한 산출물 버전에 대한 권한 있는 검수와 승인본 보관 |
| R09 | 버전과 배포 | 시험한 버전의 발행·이전 버전 복구·진행 중 실행 버전 고정 |
| R10 | 고객별 격리 | 작업공간 경계, 서버 측 자격증명 관리, 보존·삭제 정책 일치 |
| R11 | 외부 실행 | API 요청, 상태 조회, 입력 보완, 결정 제출, 산출물 조회 지원 |
| R12 | 이동 가능한 팩 | 내보내기·가져오기 때 의미 손실과 미지원 기능을 명시 |
| R13 | 선택 연동 | 외부 연결 해제나 장애가 Forge 기본 기능을 중단시키지 않음 |
| R14 | 기존 자산 호환 | 기존 CasePack·Graph·앱 주소에 대한 전환 및 회귀 검증 |
| R15 | 운영 관찰 | 오류·재시도·비용·검수 시간·업무 완료율을 구분해 관찰 |
| R16 | 사용성과 접근성 | 키보드 조작, 입력 오류 안내, 저장 상태, 중단 복귀를 확인 |

사용성 목표치는 임의의 성공 실적으로 제시하지 않는다. 예컨대 ‘첫 앱 제작 시간’은 제작자 시험에서 측정할 지표이며, 목표 수준과 표본은 B1의 사용자 검증 계획에서 정한다.

## 5. 도출할 핵심 Markdown 문서 20편

전달 패키지는 구현 티켓과 계약 파일을 포함하는 레포 문서 세트로 구성한다. 아래 20편은 제작 예정 목록이며, 이번 계획서가 해당 문서들을 대신하지 않는다.

권장 전달 폴더는 docs/upgrade/micro-agent-v2/이다. 실제 프로젝트 반영 시 기존 정본 문서의 개정 위치는 D15의 파일 단위 전환표로 확정한다.

### D00 — 00_README_AND_READING_ORDER.md

팀이 첫 번째로 읽는 안내서다. 목표 제품, 이번 범위, 문서 상태, 역할별 읽기 순서, 현재 결정과 미결정 항목, 배치 진행 상황을 담는다. 기획·프론트엔드·백엔드·QA 담당자가 자신이 읽어야 할 문서를 찾을 수 있어야 한다.

완료 기준은 모든 문서·계약·예시·티켓의 경로와 상태가 일치하는 것이다. 링크만 있고 실체가 없는 파일은 계획 상태로 명시한다.

### D01 — 01_UPGRADE_CHARTER_AND_REQUIREMENTS.md

독립 운영을 우선하는 제품 원칙, 사용자·구매자, 포함·제외 범위, R01~R16 요구사항, 출시 단계와 성공 지표를 정의한다. 외부 Work OS 없이도 검수·산출물 관리가 가능해야 한다는 요구를 명시한다.

각 요구사항은 담당 문서, 구현 티켓, 검증 시나리오와 연결한다. 새 요구가 추가되면 영향 범위와 변경 이유를 남긴다.

### D02 — 02_AS_IS_CODE_AUDIT_AND_GAP_MAP.md

현재 파일과 실행 경로를 확인해 재사용·보완·신규·전환 대상을 구분한다. Mock 경로, 실제 모델 어댑터, 입력 직렬화, 형식 검증, JSON 파싱 실패, 그래프 실행, 테넌트 문맥, 보존 정책을 우선 조사한다.

관찰마다 파일 경로와 근거, 확인 일자, 실행 검증 여부를 붙인다. 구현 의도와 확인된 동작을 섞지 않는다.

### D03 — 03_STANDALONE_PRODUCT_PRD.md

제작자, 서비스 이용자, 검수자, 운영자의 작업을 제품 행동으로 정의한다. 핵심 여정은 만들기→시험하기→발행하기→이용하기→검수하기→다시 이용하기다.

Corporate PR을 첫 참조 상품으로 하되, 업무 범용성과 단일 호출형·다단계형의 차이를 설명한다. 마켓플레이스가 없어도 제품 가치를 증명할 수 있는 독립 실행 시나리오를 포함한다.

### D04 — 04_CREATOR_STUDIO_AND_USER_EXPERIENCE.md

템플릿에서 시작하기, 자연어로 설명하기, 실제 작업 사례에서 시작하기의 세 제작 경로를 설계한다. 기본 화면은 업무 설명, 필요한 자료, 원하는 결과, 참고 사례, 검사 기준의 언어를 사용한다. TASKFLOW 블록·JSON·실행 그래프는 상세 설정으로 둔다.

각 화면에 최초 진입, 빈 상태, 저장 중, 자료 부족, 실패, 질문 대기, 검수 대기, 재개, 발행 후 수정 상태를 포함한다. 입력 양식과 결과 화면을 함께 미리 보며 수정할 수 있게 한다.

### D05 — 05_TARGET_ARCHITECTURE_AND_MODULE_BOUNDARIES.md

Forge가 자체 보유할 제작·등록·실행·검수·보관 기능과 외부 어댑터를 분리한다. 기존 packages/core, casepack, bridge, runtime, ui-forge, validation, domain-packs 및 apps/web에 책임을 배치한다.

새 패키지 추가는 기존 경계로 해결되지 않을 때 결정한다. 작성 화면·공개 앱·외부 API가 동일한 실행 서비스를 사용하도록 한다. 실행 엔진 선정은 요구사항 비교와 ADR로 확정하며, 프레임워크 도입 자체를 목표로 삼지 않는다.

### D06 — 06_CANONICAL_OBJECTS_AND_STATE_CONTRACTS.md

재사용할 정의와 고객별 설정, 개별 실행을 구분한다. 최소 객체군은 CasePackDefinition, AgentApplication, WorkRequest, Run, ArtifactVersion, ReviewDecision, EvaluationReport와 ReleaseManifest다. 자료·근거 객체와 이들 사이의 참조도 정의한다.

생성·검증·검수·배포 상태를 하나의 success로 합치지 않는다. 각 객체의 소유자, 상태 전이, 수정 가능 범위, 식별자, 버전 규칙을 명시한다. 영속 저장 형식과 공개 응답 형식은 필요한 범위에서 분리한다.

### D07 — 07_TASKFLOW_COMPILER_AND_AUTHORING_CONTRACT.md

자연어와 사례 기반 작성 내용에서 TASKFLOW 명세, 실행 계약, 평가 규칙, UI 초안을 도출하는 절차를 정의한다. AI가 제안한 규칙은 확정 전까지 초안이며, 실행 가능한 규격으로 검사한다.

기존 R_role과 A 기반 구조, TASKFLOW v2·v2.1 계보를 버전별 어댑터로 수용한다. 입력 스키마 버전과 상품 버전을 구분하고, 변환 전후 대응표를 보존한다. QPE 수행 우선순위, 실행 권한, 결과 평가 기준을 각각 관리한다.

### D08 — 08_KNOWLEDGE_CASES_AND_EVIDENCE.md

전문 지식, 긍정·실패 사례, 고객 입력, 확인된 사실, 미확인·상충 정보의 저장과 사용 규칙을 정의한다. 출처 위치, 자료 버전, 이용 권한, 갱신일, 고객 범위와 결과의 근거 연결을 포함한다.

자료 수집·검색은 최소 필요 기능부터 구현한다. Graph RAG나 지식그래프 전체 구축을 선행 조건으로 두지 않는다. 고객 실행이 끝났다는 이유로 해당 자료를 공용 지식이나 정답 사례에 자동 편입하지 않는다.

### D09 — 09_RUNTIME_ORCHESTRATION_AND_TOOL_EXECUTION.md

실제 모델 어댑터, 단일 실행, 단계 연결, 조건 분기, 추가 질문, 검수 대기, 재시도, 취소, 예산, 시간 초과, 작업 재개를 정의한다. 장시간 작업은 요청 처리와 실행 작업을 분리하고 상태를 영속 저장한다.

도구는 허용된 입력·출력·권한과 부수 효과를 선언한다. 외부 상태 변경에는 중복 실행 방지, 결과 확인, 불확실한 성공 상태 처리 기준이 필요하다. 체크포인트만으로 정확히 한 번 실행이 보장된다고 표현하지 않는다.

### D10 — 10_EVALUATION_AND_RELEASE_QUALIFICATION.md

형식 검사, 결정론적 업무 검사, 모델 평가, 사람 평가를 구분한다. 긍정·실패·경계 사례, 반복 실행, 기준 버전 비교, 중대 실패 조건, 미측정 상태, 버전 승격과 회귀 판정 방법을 정의한다.

모델 평가 점수만으로 납품 가능 상태를 부여하지 않는다. 평가 데이터와 개발 사례를 구분하고, 일부 미사용 사례를 별도 검증에 활용한다. 제작 초안·시험 완료·현장 검증을 별도 성숙도로 표시한다.

### D11 — 11_NATIVE_REVIEW_AND_ARTIFACT_WORKSPACE.md

Forge 내부 검수함, 수정 요청, 차이 비교, 승인, 산출물 버전, 다운로드, 보관과 재사용을 정의한다. 승인에는 인증된 결정자, 대상 버전 또는 내용 해시, 적용 범위, 시각과 필요 시 만료 조건을 연결한다.

승인 후 내용이 바뀌면 필요한 검수를 다시 수행한다. 외부 Work OS 연결 여부와 무관하게 이 흐름이 작동해야 한다. 외부 승인 위임 시의 권한 범위와 책임은 D13과 일치시킨다.

### D12 — 12_DATA_TENANCY_SECURITY_AND_OPERATIONS.md

DB 변경, 작업공간 격리, RLS, 역할, 자격증명 보관, 공개 앱 이용 제한, 사용량 한도, 보존·삭제, 로그의 민감정보 처리를 정의한다. 입력 문서 속 지시가 상위 정책이나 도구 권한을 바꾸지 못하도록 실행 계층에서도 제어한다.

zeroRetention의 의미는 입력·출력·첨부·추적·이벤트·백업 등 저장 위치별로 정의한다. 최소 운영 계측과 고객 콘텐츠 보존 정책을 구분한다. 장애 관찰, 비용 제한, 복구와 운영자가 확인할 화면도 포함한다.

### D13 — 13_PUBLIC_API_EVENTS_AND_INTEROPERABILITY.md

외부 시스템이 에이전트를 찾고, 실행하고, 자료를 보완하고, 상태를 구독하고, 권한 있는 검수 결정을 제출하며, 산출물을 받는 계약을 정의한다. OpenAPI, 이벤트 스키마, 오류·재시도 규칙의 설명서 역할을 한다.

인증 주체·작업공간·소유권·승인 권한·멱등성·이벤트 순서·재전송·내보내기 정책을 포함한다. 특정 외부 프로젝트 이름이 핵심 도메인 객체나 실행 코드에 박히지 않게 한다.

### D14 — 14_REFERENCE_AGENTS_AND_INTEGRATION_RECIPES.md

첫 참조 구현은 Corporate PR 제작·검수 에이전트다. 두 번째는 단일 단계의 FAQ 또는 입력 정리 에이전트로 정해, 모든 서비스에 복잡한 체인이 필요하지 않음을 보여준다.

자료 접수부터 산출물 승인까지 일관된 예시 ID와 데이터를 사용한다. 외부 시스템을 흉내 내는 최소 클라이언트로 실행·조회·결정·이벤트 수신을 검증한다. TF-Studio·DualBrain·KHERE·AI홈피 연결은 이 표준 인터페이스의 적용 예시로 작성한다.

### D15 — 15_MIGRATION_COMPATIBILITY_AND_ROLLOUT.md

기존 CasePack·Graph·앱 주소·DB·문서의 유지·변환·대체 범위를 파일 또는 객체 단위로 정리한다. 레거시 읽기, 새 버전 작성, 사전 변환 검사, 백업, 점진 전환, 이전 버전 복구 절차를 정의한다.

진행 중 실행은 시작 당시 정의·모델·자료·평가 정책 버전을 고정한다. 활성 버전을 바꿔도 진행 중 실행의 의미가 바뀌지 않아야 한다. 파괴적인 변환을 기본 경로로 두지 않는다.

### D16 — 16_ACCEPTANCE_GOLDEN_E2E_AND_CONTRACT_TESTS.md

독립 운영, 비개발자 제작, 자료 부족, 상충 수치, 실행 오류, 승인, 버전 변경, 테넌트 격리, 보존·삭제, 외부 API와 이벤트의 검증 시나리오를 정의한다.

각 시나리오는 초기 조건, 입력, 사용자·시스템 행동, 기대 상태, 기대 산출물, 확인 근거와 실패 조건을 갖는다. 시뮬레이션·실제 모델·실제 배포 환경 검증을 구분한다.

### D17 — 17_IMPLEMENTATION_BATCHES_AND_WORK_ORDERS.md

개발 순서, 선행 조건, 대상 모듈·파일, 필요한 마이그레이션, 구현 작업, 검증 명령, 완료 증거와 복구 방법을 티켓으로 분해한다. 티켓별로 관련 요구사항과 명세를 연결한다.

현재 레포의 typecheck·test·build·fixtures:validate 등의 스크립트를 확인해 사용한다. 필요한 검사만 단계에 맞춰 지정하고, 실행하지 않은 명령을 성공으로 기록하지 않는다.

### D18 — 18_TEAM_HANDOFF_RUNBOOK_AND_RELEASE_CHECKLIST.md

개발팀이 로컬 실행부터 첫 앱 발행과 운영 점검까지 따라갈 절차를 제공한다. 설치·환경변수의 이름과 용도, 샘플 자료, 모델 연결, DB 준비, 실행·검수·오류 확인, 외부 연동 확인을 담는다. 실제 비밀값은 포함하지 않는다.

문서 동결 시점, 변경 승인 주체, 버전 기록, 알려진 제약, 미해결 결정, 지원 담당 역할을 명확히 한다. 문서 세트의 전달 완료와 소프트웨어 출시 완료를 분리한다.

### D19 — 19_SOURCE_EVIDENCE_AND_DECISION_REGISTER.md

교재와 소스에서 가져온 사실, 설계 해석, 신규 제안을 구분한다. 모든 주요 결정에 근거, 대안, 선택 이유, 영향 범위와 재검토 조건을 붙인다.

1급 교재 원문이 확보되지 않은 상태를 명시하고, TASKFLOW→CogCL/QPE 전이 가이드를 1급 공식 교재로 호칭하지 않는다. 프레임워크·API·표준의 구체적 버전은 해당 문서 제작 시 공식 문서에서 재확인한다.

## 6. 설명 문서와 함께 도출할 기계 판독 파일

문서만으로 구현자가 서로 다른 해석을 하지 않도록 계약과 예시를 함께 만든다. 아래 파일은 도출 계획이며, 현재 제공되는 실행 파일이 아니다.

### 6.1 요구사항과 파일 목록

manifest.json에는 문서·계약·예시의 경로, 버전, 상태, 의존 문서, 담당 역할을 기록한다. requirements-traceability.csv에는 요구사항→문서→계약→티켓→테스트→실행 증거의 연결을 기록한다. CSV의 값은 Markdown 문서에 중복 수기 관리하지 않고 추적표를 기준으로 점검한다.

### 6.2 계약 스키마

schemas/ 아래에는 CasePackDefinition, AgentApplication, WorkRequest, RunReceipt, ArtifactVersion, ReviewDecision, EvaluationReport, ReleaseManifest와 이벤트 봉투의 스키마를 마련한다. 실제 레포의 Zod 정의를 정본으로 할지 별도 규격을 정본으로 할지는 B1에서 확정한다. 권고안은 기존 Zod 체계를 유지하고 배포용 JSON Schema를 생성·검증하는 방식이다.

공통 식별자·상태·버전·공개 범위는 한 곳에서 정의한다. 문서와 JSON과 TypeScript가 서로 다른 상태 이름을 수기로 유지하지 않도록 한다. JSON Schema로 표현하지 못하는 도메인 규칙은 실행 검사와 부정 사례로 보완한다.

### 6.3 외부 인터페이스

contracts/openapi.yaml, contracts/asyncapi.yaml 및 이벤트 예시를 도출한다. 선택할 규격 버전과 검증 도구는 B3에서 확인한다. 첫 외부 클라이언트에 필요한 최소 기능부터 완성하며, SDK·MCP·워크플로 플랫폼별 내보내기는 후속 확장으로 구분한다.

### 6.4 정상·실패·경계 사례

examples/에는 최소한 단일 에이전트, 다단계 문서 에이전트, 자료 부족, 상충 사실, 검수 대기, 승인 후 변경, 외부 요청 중복, 이벤트 재전송, 미지원 도구 팩 가져오기 사례를 둔다.

케이스마다 기대 상태와 산출물을 연결한다. 실제 고객 정보 대신 합성·비식별 예시를 사용한다. 데모 응답은 모의 실행임을 표시하며 실제 모델 결과와 혼합하지 않는다.

### 6.5 개발 작업 지시와 검증 도구

tickets/의 각 지시서는 목적, 변경 범위, 선행 계약, 구현 단계, 완료 기준, 검사 명령과 복구 방법을 갖는다. tests/에는 계약 검사와 평가 실행의 설계 또는 실제 테스트 파일을 상태에 맞게 둔다. 문서 도출 단계에서 테스트 코드를 작성하더라도 프로젝트에 연결하여 실행하기 전에는 ‘미실행’으로 표시한다.

## 7. 독립 제작 경험의 구체적인 설계 범위

### 7.1 제작자는 업무 언어로 시작한다

입력하는 첫 정보는 업무 목적, 고객, 필요한 자료, 기대 결과, 잘된 사례, 주의할 조건이다. 시스템은 초안을 제안하고, 제작자는 예시 결과를 보며 수정한다. 처음부터 TF8 전체 칸이나 복잡한 그래프를 강제로 작성하게 하지 않는다.

단순 작업은 단일 CasePack으로 끝낼 수 있어야 한다. 질문·분기·검수가 필요한 경우에만 연결 실행을 추가한다. 전문가가 사례와 평가 기준을 충분히 제공하지 않았으면 초안 상태를 유지하고, 검증된 전문성이나 정확도를 표시하지 않는다.

### 7.2 시험 화면이 제작의 중심이 된다

제작자는 왼쪽에서 기준을 바꾸고, 오른쪽에서 입력 예시·결과·검사 내용을 비교한다. 시스템은 어떤 기준이 바뀌었고 어떤 평가 사례가 실패했는지 알려준다. 입력 누락을 임의로 채우거나 예시의 수치를 고객 사실로 사용하는 오류를 확인할 수 있어야 한다.

모든 설정을 자동 추출했다고 즉시 발행하지 않는다. 제작자가 제공 서비스 범위, 검수 조건, 사용 지식, 공개 범위를 확인한 버전만 발행한다.

### 7.3 운영과 수정도 같은 제품 안에서 끝난다

실행 목록에서 진행·질문·검수·실패 상태를 확인하고 필요한 작업을 이어간다. 결과에는 본문, 사용 근거, 미확인 항목, 검사 결과를 적절히 구분해 제공한다. 공개 화면에는 내부 프롬프트나 비공개 참고 자료 전체를 노출하지 않는다.

서비스 수정 시 새 버전을 만들고, 변경 전후 평가를 비교한 후 적용한다. 고객 설정이나 고객 자료를 공통 CasePack에 섞지 않는다.

## 8. 외부 시스템 연동 인터페이스의 도출 원칙

### 8.1 기본은 API·이벤트·표준 산출물이다

첫 연결은 일반 HTTP API, 상태 조회, 서명된 Webhook, 권한이 있는 산출물 조회로 해결한다. MCP는 기존 API를 활용하는 추가 어댑터 후보로 둔다. MCP를 지원한다고 모든 에이전트 호스트에서 동일한 권한·평가·실행 의미가 보존된다고 표현하지 않는다.

외부 시스템이 연결되지 않은 상태에서도 동일 기능을 Forge 내부 화면에서 사용할 수 있어야 한다. 비밀값이나 서명 URL은 팩 내보내기 파일에 넣지 않는다.

### 8.2 제안 API 표면

아래 경로는 설계 초안이다. B3에서 기존 경로와의 충돌, 인증 구조, 응답 호환성을 검토해 확정한다.

- GET /api/v1/capabilities: 지원하는 계약 버전·입력·출력·도구 기능 확인.
- POST /api/v1/runs: 발행된 앱 또는 고정된 릴리스에 대한 실행 요청.
- GET /api/v1/runs/{run_id}: 생성·검증·검수 상태와 다음 행동 확인.
- POST /api/v1/runs/{run_id}/inputs: 요청된 추가 자료 제출.
- POST /api/v1/runs/{run_id}/decisions: 권한 있는 검수 결정 제출.
- POST /api/v1/runs/{run_id}/cancel: 실행 취소 요청과 처리 결과 확인.
- GET /api/v1/artifacts/{artifact_id}/versions/{version}: 접근 가능한 특정 산출물 버전 조회.

비동기 실행 요청은 접수와 완료를 구분한다. 실행 요청에는 호출자 인증, 작업공간, 외부 업무 참조, 대상 릴리스, 입력, 검수 권한 방식, 상관 식별자와 멱등 키를 연결한다. 같은 키와 같은 내용의 요청은 기존 실행을 반환하고, 내용이 바뀌면 충돌로 처리하는 계약을 마련한다.

### 8.3 이벤트와 오류는 구현 전에 의미를 확정한다

run.started, run.input_required, review.requested, run.completed, run.failed, run.cancelled, artifact.ready 등을 후보로 한다. 이벤트 이름과 payload는 D06 상태 계약과 함께 확정한다. run.completed가 자동으로 전문가 승인이나 외부 주문 완료를 의미하지 않게 한다.

이벤트 봉투에는 event_id, event_type, schema_version, occurred_at, workspace_id, run_id, correlation_id와 필요한 최소 payload를 둔다. Webhook은 중복·순서 역전·지연을 전제로 수신자가 처리할 수 있어야 한다. 서명 검증·재전송·오류 큐·정상 상태 재조회와 민감정보 제외 규칙을 정의한다.

이벤트 버전은 단순 문자열 순서로 실행 상태를 판정하지 않도록 설계한다. 수신자가 놓친 이벤트를 복구할 수 있는 조회 계약을 마련한다. 임의의 콜백 주소로 내부망에 접근하지 못하도록 등록·허용 정책도 둔다.

### 8.4 외부 검수는 권한 위임이지 상태 덮어쓰기가 아니다

외부 시스템이 approved=true를 보내는 것만으로 승인 상태를 바꾸지 않는다. 위임받은 주체인지, 해당 작업과 산출물 버전에 대한 권한이 있는지 확인한다. 결정에는 actor, authority, artifact_version 또는 hash, decision, reason, timestamp를 연결한다.

연동 작업에서 외부 검수 시스템이 응답하지 않으면 대기 상태를 유지한다. 담당자가 Forge에서 대신 결정할 수 있는지는 작업 생성 시 정한 권한 정책을 따른다. 임의의 자동 승인으로 전환하지 않는다. 독립 작업에는 외부 장애가 영향을 주지 않아야 한다.

### 8.5 팩의 이동성과 실행 보장은 구분한다

내보내기에는 업무 정의, 입출력 규격, UI 설정, 사례, 평가 규칙, 의존 도구와 최소 실행 기능 목록을 포함한다. 고객 비공개 자료와 자격증명은 기본 제외한다.

가져오기 시 지원 여부, 버전 호환성, 필요한 자료·도구, 누락된 권한을 검사한다. 지원하지 않는 사람 승인이나 도구 기능을 자연어 프롬프트로만 바꾸고 동일하게 실행된다고 표시하지 않는다. 실행 불가 또는 기능 제한을 명확히 보여준다.

## 9. 문서 도출 배치와 검수 순서

문서 작성 배치와 소프트웨어 구현 배치는 별개다. 아래 B0~B5는 문서 세트를 만드는 순서다.

### B0 — 현재 상태와 범위 고정

D00·D01·D02·D19를 작성한다. 기존 문서와 코드의 위치, 재사용 대상, 변경 범위, 근거의 상태를 확정한다. 최신 코드와 이전 관찰이 다르면 최신 확인 근거를 우선한다.

완료 조건은 ‘무엇을 만들며 무엇은 후속인가’와 ‘현재 무엇이 있는가’가 구분되는 것이다. 1급 원문 미확보 등 자료의 공백도 이 단계에서 기록한다.

### B1 — 독립 제품과 공통 객체 설계

D03·D04·D05·D06을 작성하고 D13의 소유권·식별자·API 기본 흐름 초안을 병행 정의한다. 대표 사용자 시나리오와 화면 상태를 객체·상태 계약에 연결한다.

완료 조건은 외부 시스템 없이 제작·실행·검수·납품이 가능하며, 같은 객체를 외부에서 어떻게 요청·참조할지가 설명되는 것이다.

### B2 — 작성에서 실행·평가까지 연결

D07·D08·D09·D10을 작성한다. TASKFLOW 호환, 지식과 자료 분리, 실제 모델 실행, 중단·재개, 품질 평가와 출시 판정을 하나의 대표 사례로 연결한다.

완료 조건은 입력→정규화→실행→검사→결과의 필드와 상태가 일치하는 것이다. 지원하지 못하는 정책은 실행 가능으로 표시하지 않는다.

### B3 — 검수·데이터·외부 인터페이스 확정

D11·D12·D13을 완성하고 스키마, OpenAPI, 이벤트 계약을 도출한다. 인증·권한·보존·소유권을 화면과 API 양쪽에 동일하게 적용한다.

완료 조건은 API의 정상·오류·중복·권한 거부·재전송 사례를 설명할 수 있고, 외부 시스템을 흉내 낸 클라이언트로 검증할 계약이 마련되는 것이다.

### B4 — 참조 팩·전환·검증 시나리오 작성

D14·D15·D16과 정상·실패·경계 예시를 작성한다. Corporate PR 전체 흐름과 단일 에이전트 예시, 레거시 변환 전후 예시, 외부 연동 예시를 검증한다.

완료 조건은 각 요구사항에 검증 시나리오가 연결되고, 예시 파일이 해당 스키마와 일치하는 것이다. 코드가 아직 없으면 실행 검증 상태를 NOT_RUN으로 유지한다.

### B5 — 개발 작업 지시와 최종 전달

D17·D18을 작성하고 D00·D19·manifest·추적표를 갱신한다. 파일 단위 구현 범위, 선행 조건, 검사 방법, 문서 정합성, 남은 결정 항목을 점검한다.

전달물은 Markdown 원본, 계약·예시·티켓·검증 결과, README와 전체 ZIP이다. 개발팀에게 실제 메시지를 보내거나 저장소를 변경하는 행위는 문서 작성과 별도 작업으로 취급한다.

## 10. 개발팀의 구현 순서로 연결하는 방법

### I0 — 실제 업무 실행 기반

실제 모델 연결, 입력·출력 보존, 형식 검사와 업무 평가 연결, 인증된 작업공간, 기본 산출물 저장을 먼저 구현한다. 하나의 참조 팩을 실제 모델로 실행하고 모의 실행과 구분한다.

### I1 — 독립 제작과 납품 완주

템플릿 기반 제작기, 테스트 화면, 발행·버전 고정, 고객 입력, 기본 검수함, 다운로드를 연결한다. 외부 시스템 없이 첫 앱을 만들고 실제 자료로 결과를 제공한다.

### I2 — 반복 운영과 지속 실행

질문·검수 대기, 서버 재시작 후 재개, 재시도 예산, 고객별 설정, 자료·산출물 버전, 평가 회귀와 복구를 구현한다. 다시 실행했을 때 이미 완료한 외부 작업이 중복되지 않는지 확인한다.

### I3 — 공개 연동과 한 개의 실제 연결

B1부터 준비한 외부 계약을 제품으로 제공한다. 최소 외부 클라이언트 검증 후, 보유 시스템 한 곳을 선택해 연결한다. 여러 시스템의 전체 통합을 최초 출시 조건으로 삼지 않는다.

교육 연동과 외부 주문 연동은 서로 다른 목적이므로 첫 연결의 목표를 먼저 확정한다. 이후 동일한 API와 이벤트를 이용해 다른 시스템을 추가한다.

## 11. 반드시 포함할 인수 시나리오

- AT01: 외부 연결을 전부 비활성화한 상태에서 템플릿 선택→작성→시험→발행→고객 실행→검수→다운로드를 완주한다.
- AT02: 비개발자가 JSON을 수정하지 않고 단일 에이전트를 만들고 입력·결과 화면을 변경한다.
- AT03: 기존 R_role 기반 팩을 읽고 변환한 뒤 핵심 업무 의미와 입출력 계약을 보존한다.
- AT04: 필수 고객 자료가 없으면 추가 입력 상태가 되며, 가짜 사실로 완료하지 않는다.
- AT05: 상충하는 수치를 감지하고 확인 또는 사용 제외를 요청한다.
- AT06: 모델의 잘못된 JSON, 시간 초과, 제공자 오류를 서로 구분하고 정해진 한도 안에서 처리한다.
- AT07: 검수 대기 후 프로세스가 재시작되어도 해당 작업과 자료·버전을 복구한다.
- AT08: 승인된 산출물을 수정하면 버전이 바뀌고 필요한 승인 효력을 다시 판단한다.
- AT09: 다른 작업공간의 자료·실행·산출물·결정에 접근하거나 변경하지 못한다.
- AT10: 자료 보존 및 삭제 정책이 입력·출력·첨부·추적 저장소에 일관되게 적용된다.
- AT11: 같은 멱등 키와 같은 실행 요청을 재전송해 중복 업무를 만들지 않는다.
- AT12: 중복·역순 Webhook을 받아도 외부 상태가 잘못 후퇴하거나 중복 납품되지 않는다.
- AT13: 승인 권한이 없는 외부 호출과 오래된 산출물에 대한 결정이 거절된다.
- AT14: 미지원 도구·승인 기능을 가진 팩을 가져오면 기능 제한 또는 실행 불가를 명시한다.
- AT15: 활성 팩 버전이 바뀌어도 진행 중 실행은 시작 당시 버전을 사용한다.
- AT16: 외부 연결 장애 중에도 독립 작업이 정상 동작하고, 외부 결정에 의존하는 작업은 정책에 따라 대기한다.
- AT17: 새로운 자료로 재실행할 때 변경된 결과와 사용 근거를 식별할 수 있다.
- AT18: 공개 앱 응답과 내보내기에 비밀값·내부 프롬프트·다른 고객 자료가 포함되지 않는다.

각 시나리오는 문서 세트 제작 시 상세 Given/When/Then과 증거 위치를 추가한다. 현재 목록은 테스트 결과가 아니다.

## 12. 문서 세트의 품질 기준

문서 수보다 구현 결정의 완결성을 기준으로 검수한다. ‘권한을 고려한다’ 대신 누가 어떤 객체에 무엇을 할 수 있는지 정의하고, ‘품질을 보장한다’ 대신 어떤 검사를 수행하며 실패·미검증 상태를 어떻게 처리하는지 적는다.

필수 정합성 검사는 다음과 같다.

1. 요구사항 R01~R16이 문서·티켓·검증 시나리오에 연결되어 있다.
2. 객체·상태·이벤트·API·화면의 이름과 의미가 일치한다.
3. 예시가 계약 스키마를 통과하고, 실패 예시는 기대한 이유로 실패한다.
4. 독립 모드에 외부 사업 시스템의 필수 의존성이 없다.
5. 검수 주체와 산출물 버전이 명확하며 임의의 상태 덮어쓰기가 없다.
6. 기존 팩·앱·데이터의 전환 방법과 복구 방법이 있다.
7. 비개발자의 제작·실행·수정 흐름이 화면 수준에서 설명된다.
8. 확인 사실, 설계 제안, 실행 결과, 미검증 사항이 구분된다.
9. 실제 코드와 호환되는 명령·경로를 사용하며, 비밀값과 고객 원문을 포함하지 않는다.
10. 개발자가 문서만 읽고 첫 구현 배치에 착수할 수 있는 작업 지시가 있다.

문서상 미결정 항목은 숨기지 않되, 모든 선택을 팀에 떠넘기지 않는다. 각 항목에 권고안, 대안, 확정 시점과 결정 역할을 기록한다.

## 13. 문서 도출 시 확정할 주요 결정

- 공통 스키마의 정본과 생성 경로: 기존 Zod 중심 유지 권고.
- 장시간 실행 엔진: 영속 상태·중단·재개·실행 격리 요구로 후보를 비교한 후 결정.
- 첫 모델 제공자: 현재 어댑터에 실제 제공자 한 곳을 우선 연결하고 추가 제공자는 후속 검증.
- 자료 검색 범위: 기본 파일·출처 검색을 먼저 제공하고 고급 검색은 실측 필요에 따라 확장.
- 최초 외부 연동 대상: 교육 과제 수입 또는 외부 업무 의뢰 중 첫 실증 목적에 맞춰 하나 선택.

## 15. 이번 계획서의 전달 범위

이번 산출물은 고도화 개선 레포 문서 세트를 도출하기 위한 계획서 한 편이다. 실제 20편의 명세, 계약 스키마, 참조 팩, 개발 티켓과 테스트는 B0~B5 순서로 작성할 후속 산출물이다. 기존 프로젝트의 코드나 문서를 변경하지 않았고, 개발팀에 메시지를 발송하지 않았다.

후속 제작의 첫 결과는 B0의 범위·요구사항·코드 갭·근거 목록이며, 최종 결과는 독립 운영과 외부 연동을 함께 설명하고 검증할 수 있는 개발팀 전달 패키지다.
